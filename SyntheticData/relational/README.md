# 관계형 합성 데이터 (v2) · N:N 복합 질의

v1(`../commerce`, `../trading`)은 표마다 따로 노는 단조로운 데이터였습니다. 주문자 · 리뷰 작성자가 매번 새 사람이고, 쿠폰 · 이벤트가
주문과 이어지지 않았으며, 질의도 표 하나만 보는 것(식별자 · 상태 · 금액 · 기간 · 의미)이었습니다. v2 는 **한 세계에서 커머스 ·
무역 · 행동 로그가 같은 식별자로 엮이고**, 질의가 **표 두 개 이상을 건너는** 데이터입니다.

```
world.py              세계: 쇼핑몰 4곳(ko · en · ja · de) × 회원 12 · 상품 18 · 주문 32 · 운송장 31~45 · 리뷰 14 · 쿠폰 4 · 이벤트 3
render.py             커머스 관리자 화면(admin_flat) 11장/쇼핑몰. 관계는 링크(od_id · it_id · invoice · cp_id · ev_id)로 드러남
trade.py              무역: 쇼핑몰마다 수입 거래 1건(PO 1 → 분할 선적 2회, L/C 1). 서류 7장, 수출자 언어로(de · ja · ko · en)
weblog.py             행동 로그: Cloudflare D1 행 모양의 원시 이벤트 374건(도메인 4 × 세션 15), 도메인 · 웹 경로 정의
queries.py            N:N 복합 질의: 틀 23개 × 사례 33 × 12개 언어 = 396, 행동 로그 보류 72(틀 A1 ~ A6 × 다른 쇼핑몰) → 468
generate_relational.py  위를 모두 쓰는 생성기 (--check 로 재현 확인)
make_plans.py         평가 계획: 검색 저장소(seed2 · analytic) · 검색 질의
score_relational.py   채점: 화면 순서를 main.ts 그대로 재현 (계획 거르기 → 구출 → 연결 1 · 2단), 추출 대조
```

다시 만들기: `python generate_relational.py` (PDF 는 reportlab 이 있는 파이썬), 같은지 확인은 `--check`.

## 세계

- **회원이 여러 번 삽니다.** 단골 몇 명에게 주문이 몰리고, 25 % 는 선물(받는 사람이 다른 회원)입니다.
- **주문 → 상품 1~3개 · 쿠폰 · 이벤트 · 운송장 1~3개.** 상품이 둘 이상이면 45 % 는 나눠 보내고(부분 배송), 반품 주문에는 회수 운송장이
  하나 더 붙습니다. 이벤트 기간에는 이벤트 상품이 담기고 이벤트 쿠폰이 쓰입니다.
- **리뷰 → 그 회원이 실제로 받은 주문의 상품.** 반품 주문의 리뷰는 별점이 낮습니다.
- **무역 → 커머스.** 수입 품목 3개의 품목 번호(item_code)가 쇼핑몰의 상품 번호입니다. 1차 선적(품목 2개)은
  CI · PL · BL · CO · IP, 2차 선적(품목 1개)은 CI · BL 이고 서류끼리 번호로 가리킵니다(CI → PO · BL · LC, BL → CI · PO · LC ...).
- **행동 로그 → 커머스.** 구매 세션은 실제 주문(이벤트 페이지 → 상품 → 장바구니 → 결제 → 주문 완료 `orderNo`)이고, 장바구니 이탈 ·
  리뷰 작성 · 검색 · 쿠폰 받기 세션이 있습니다. 상품 · 주문 · 이벤트 번호는 URL 매개변수(goodsNo · orderNo · eventNo)라 앱의
  구조화 단계가 상품 · 주문 연결을 새깁니다.

네 쇼핑몰은 **같은 테마(admin_flat)** 라서 언어 사이의 차이가 레이아웃 차이와 섞이지 않습니다. 화면 문구 · 상태어 · 날짜 · 금액 · 사람 이름 ·
상품 이름은 v1 생성기와 언어 팩(`../commerce/lang_packs`)을 그대로 씁니다.

## 도메인 · 웹 경로 정의 (행동 로그)

`weblog/sites.yaml` 이 정의입니다. 사이트 4개(host · 이름 · 언어)와 경로 10종(home · goods_list · goods_view · search · cart · checkout ·
order_complete · event_view · mypage_orders · review_write). 앱 쪽 정의는 `bias.json` 의 `analytic_page_filters`(경로 접두 + 12개 언어 문구)이고,
구조화가 행동 로그에 `host` · `path` · `page` 를 남기며, 검색은 질의에 나온 사이트 이름으로 사이트를 좁히고 페이지 문구로 페이지 종류를 거릅니다.

Worker(console.logis.center)가 연결되어 있지 않아, 원시 행(`weblog/events.jsonl`)을 앱의 동기화와 같은 명령 순서
(`upsert_items` → `structure_pending_analytics` → `reindex_pending_embeddings`)로 넣습니다: 하네스의 `analytic` 작업 → `eval_analytic_ingest`.

## 질의 (N:N)

| 틀 | 건너는 표 | 틀 | 건너는 표 |
|---|---|---|---|
| C1 주문 → 운송장 | order → tracking | R1 B/L 관련 서류 | BL → CI · PL · CO · IP |
| C2 운송장 → 주문 | tracking → order | R2 PO 의 B/L | PO → BL × 2 |
| C3 고객이 산 상품 | 고객 → order → goods | R3 B/L 의 송장 | BL → CI |
| C4 그 달 그 상품 주문 | goods + 기간 → order | R4 L/C 의 송장 | LC → CI × 2 |
| C5 쿠폰 쓴 주문 | coupon → order | R5 수출자의 B/L | 당사자 → BL × 2 |
| C6 이벤트 상품 | event → goods | R6 품목을 실은 B/L | 품목 → BL |
| C7 이벤트 기간에 팔린 상품 | 기간 → order → goods | R7 그 달 그 항구 서류 | 항구 + 기간 → 서류 |
| C8 고객이 리뷰한 상품 | 고객 → review → goods | A1 사이트 장바구니 | 사이트 + 행동 |
| C9 반품 주문의 상품 | 상태 → order → goods | A2 상품 페이지 옵션 변경 | 사이트 + 페이지 + 행동 |
| C10 그 달 그 고객 배송 | 고객 + 기간 → tracking | A3 상품을 담은 기록 | 상품 + 행동 |
| | | A4 결제까지 갔다가 이탈 | 사이트 + 페이지 |
| | | A5 이벤트 페이지 쿠폰 | 이벤트 페이지 + 행동 |
| | | A6 기간 모바일 터치 | 사이트 + 기간 + 기기 |

- 커머스 틀은 쇼핑몰 2곳(데이터 언어 2개), 무역 · 행동 틀은 1곳에 사례 하나씩. **모든 질의 언어가 같은 사례를 묻습니다** — 언어 비교가 공정합니다.
- 슬롯: 상품 이름은 **질의 언어의 이름**(번역 — 언어 건너기를 잼), 고객 · 쿠폰 · 이벤트 · 수출자 · 사이트 이름은 화면 그대로(데이터 언어),
  번호는 그대로, 달 · 날짜 · 항구는 질의 언어 꼴.
- 정답은 세계에서 계산합니다. 사람이 고른 예시가 아닙니다.

## 평가 절차

전처리와 검색을 따로 잽니다. 전처리 오류가 검색 점수에 섞이면 어느 언어가 검색에 약한지 알 수 없기 때문입니다.

1. **전처리(추출) 표본**: 쇼핑몰마다 주문 목록 · 배송 목록 · 주문 상세, 거래마다 CI · BL · IP 를 실제 파이프라인(`html` · `document`)으로 추출 →
   `score_relational.py extract`. (전체 44장 + 28장은 장당 5~10분이라 표본으로 잽니다 — 목록 행마다 요약 문장 생성이 돕니다)
2. **검색 저장소**: `make_plans.py` 의 `plan_store.jsonl` — `seed2` 가 세계 레코드를 추출 경로와 같은 모양(id = entity_id, data.index,
   연결 칸 = 대상 index)으로 넣고, `analytic` 이 행동 로그를 앱 동기화 경로로 넣습니다.
3. **검색**: `plan_search.jsonl`(앱 언어 korean, 커머스는 그 쇼핑몰 사이트 범위) → `score_relational.py search`.

**(4) 분할 크롭 하한 (vision_crop)**: 기획안대로 연결했고, 이 데이터에서는 거의 중립입니다. 분할 크롭 하한을 카테고리마다 그 서식의 1차 크롭 커버리지

## 한계

내가 만든 데이터라 **방향을 보여 줄 뿐 실제 성능을 뜻하지 않습니다.** 쇼핑몰 4곳 · 테마 하나 · 번역은 원어민 검수 전입니다. 질의 틀은 처음에
앱이 못 하던 것(두 단계 연결, 부정 · 세션 조건)을 일부러 포함합니다 — 점수가 낮은 틀은 '못 하는 일' 의 목록입니다. 사전 라벨 보강은 같은 합성
페이지에서 빈칸을 찾아 같은 페이지로 쟀으므로 전처리 수치가 낙관적이고, 2 ~ 4차 검색 수정도 같은 276건의 로그에서 찾았으므로 새 질의 틀에서는
더 낮을 수 있습니다. 보류 집합(커머스 120건 · 행동 로그 72건)은 사례(쇼핑몰)만 바꾼 것이고, 행동 로그 보류에서 A3 은 일반화되지 않았습니다.
비전 게이트의 열화는 합성(가우스 흐림 · 그린 도장 · 그린 서명 획)이고 3σ 는 같은 데이터로 골랐습니다.
